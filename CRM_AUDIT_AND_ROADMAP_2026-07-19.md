# ROLANPRO CRM — локальный аудит и дорожная карта

Дата аудита: 19 июля 2026 года  
Режим работы: только локальный компьютер, без публикации на сервер и без реальных отправок клиентам.

## 1. Решение по исходной базе

- Основой дальнейшей разработки является модульное приложение в этой папке: Next.js + PostgreSQL + Prisma.
- Старый монолитный файл `rolanpro-crm_3.html` хранится только как функциональный референс.
- Из `rolanpro-crm_6.html` нужно переносить визуальные идеи для premium proposal, пакеты и upsell, но не заменять им рабочую логику версии `_3`.
- Переписывать систему заново не нужно. Нужна поэтапная доработка текущего модульного приложения.

## 4.1. Реализовано в первом этапе Sales Control

- 21 технический статус сохранён в базе и объединён в 8 понятных рабочих этапов.
- Убрана бесконечная горизонтальная воронка: этапы размещаются адаптивной сеткой.
- Добавлены поиск, фильтр по источнику и фильтры «Есть просрочка» / «Нет следующего действия».
- В карточке видны сумма, источник, менеджер, подробный статус, открытые задачи и следующий контакт.
- Разрешены только последовательные переходы между статусами.
- Для перехода активной сделки обязательно следующее действие с типом и дедлайном.
- Переход и follow-up сохраняются вместе, фиксируются в activity log и синхронизируют связанный лид.
- Менеджер может менять только назначенные ему сделки; владелец сохраняет полный доступ.
- Общая мобильная оболочка менеджера стала компактной и больше не закрывает первый экран.
- Проверены production build, desktop и mobile без горизонтального переполнения.

## 5. Критические разрывы

### Воронка

- Базовая управляемая воронка реализована; следующим шагом нужны автоматические задачи и шаблоны касаний.
- Нет автоматической последовательности касаний для клиентов в ожидании ответа.

### Задачи

- Таблицы и API существуют, но нет полноценного центра задач.
- Нельзя удобно создать задачу прямо в каждом lead/deal/project и увидеть общий список по дедлайнам.
- Нет шаблонов задач, чек-листов и автоматических задач при переходах воронки.

### Proposal

- Client proposal пока функциональный, но визуально слишком простой.
- Чертежи окон не встроены в клиентское КП.
- Нет Good / Better / Best или Standard / Premium / Ultimate пакетов.
- Нет live Stripe deposit/payment link внутри клиентского сценария.
- AI не должен быть отдельной кнопкой «сделать КП». Он должен помогать с текстом, аргументами и оформлением уже рассчитанного КП.
- Нет полноценной версии предложения с блокировкой подписанной суммы.

### Монтаж

- Есть базовые статусы, но нет обязательной приемки объекта до начала.
- Нет обязательных before/after фото, чек-листа качества и фиксации дефектов.
- Нет клиентской подписи акта завершения.
- Нет правила блокировки выплаты монтажнику до завершения checklist + customer acceptance.
- Нет автоматической цепочки клиентских уведомлений «назначено → едет → прибыл → начал → закончил».
- Нет автоматического запроса отзыва и after-sale upsell после приемки.

### Финансы и склад

- Расчет себестоимости есть, но полноценного project expense register нет.
- Нет корректного разделения manager-entered operational expenses и owner-only variable costs.
- Склад, reservation, consumption, roll cutting и waste описаны в архитектуре, но не доведены до рабочего модуля.
- Payroll описан, но не реализован как законченный рабочий модуль.
- Налоги California C-Corp нельзя жестко зашивать в код: правила, ставки и категории должны быть настраиваемыми и утверждаться бухгалтером/CPA.

### Academy

- В текущем модульном приложении отсутствует полноценная Academy.
- Нужны программы обучения, материалы, тесты, сертификаты и допуски к видам работ.

### Мобильные приложения

- Текущий web-интерфейс не готов как мобильное приложение.
- На телефоне кабинет замерщика имеет горизонтальный overflow.
- В кабинете монтажника боковая панель занимает первый экран, а рабочая зона начинается ниже.
- Нужен отдельный mobile-first UX для замерщика и монтажника с offline draft, камерой и очередью синхронизации.

## 6. Утверждаемая воронка

На экране менеджера показывать 8 основных колонок, а детальные состояния хранить как substatus:

1. `Новые` — new, contact_attempted.
2. `Квалификация` — contacted, qualified, not_qualified.
3. `Консультация / Замер` — consultation_scheduled, survey_scheduled, survey_completed.
4. `КП` — proposal_draft, proposal_ready, proposal_sent.
5. `Решение клиента` — waiting_reply, follow_up, revision_requested, approved, lost.
6. `Депозит / Планирование` — agreement_signed, deposit_pending, deposit_paid, scheduling.
7. `Монтаж` — scheduled, on_the_way, in_progress, customer_acceptance.
8. `Закрытие / Aftercare` — final_payment, completed, review_requested, warranty, upsell.

Обязательное правило: активная сделка не может оставаться без `next_action`, `responsible_user` и `due_at`.

## 7. Целевая архитектура мобильных приложений

- Единый backend API и единая PostgreSQL-база.
- Desktop web CRM для Owner и Manager.
- Отдельный mobile-first field interface для Consultant и Installer уже на этапе локального утверждения.
- После утверждения логики — приложения iOS/Android на Expo React Native, использующие тот же API.
- Общие контракты API, типы, статусы и business rules должны переиспользоваться web и mobile приложениями.
- Offline draft для замеров, фото и checklist; синхронизация с idempotency keys после появления сети.

## 9. Правило дальнейшей работы

Каждый этап сначала реализуется и утверждается локально. Нельзя публиковать на сервер, подключать live Stripe, отправлять реальные SMS/email/push или запускать необратимые миграции без отдельного подтверждения владельца.

# ROLANPRO CRM / ERP — Go-live 2026-09-08

This runbook defines the operating V1 that the team can use from the first working day. It intentionally separates launch-critical workflows from later ERP normalization work.

## One entry point

Use the production `/legacy-crm` workspace for every employee role.

- Owner: full company workspace and owner-only economics.
- Manager: sales, customer/project operations, pricing allowed by role, planned and actual project expenses.
- Consultant / Surveyor: assigned operational records only.
- Installer: assigned work, workday, mileage, job progress, own payroll history.

Do not train employees on `/owner/*`, `/manager/*`, `/survey/*`, or `/installer/*` as separate CRMs. Those addresses are compatibility routes only.

## Day-one sales workflow

1. Create or open the Lead / Deal.
2. Use `Калькулятор` for the 30–60 second preliminary calculation.
3. Add planned object expenses such as lift, delivery, parking, electrician, rental, subcontractor.
4. Save the estimate into the Deal as a draft proposal.
5. If an on-site visit is needed, create/complete consultation and survey.
6. Record rooms / windows / measurements and select the exact film only when known.
7. Prepare and send the canonical Proposal.
8. Obtain Agreement signature.
9. Record the required Deposit as paid.
10. Only after BOTH Agreement + Deposit, use the explicit project launch action. This is the step that creates the PRJ project number.

A customer who is still thinking remains in Sales / Follow-up. Do not create an operational Project just to reserve a possible job.

## Day-one project workflow

1. Project positions come from the approved proposal and exact service/film information.
2. Confirm schedule / phase and crew.
3. Assign installer work.
4. Installer uses `Рабочий день` and the assigned job workflow for shift, mileage and execution status.
5. Completion creates/uses the existing installer payroll accrual flow.
6. Manager records every real object expense in `Деньги` on the day it is paid or incurred.
7. Compare `План доп. расходов` with `Факт` and investigate overruns immediately.

## Money discipline from day one

`Калькулятор` = planned object expenses.

`Деньги` = actual paid/incurred object expenses.

For each actual expense record:

- Deal or Project
- category
- amount
- payment method
- date
- short note/vendor context

Example:

- Plan: `Lift — $650`
- Actual: `Lift / Scaffold — $720`
- Variance: `+$70` over plan

The launch V1 expense ledger is stored in PostgreSQL activity history with actor/date/scope. It is append-only in the current UI so the first-day audit trail cannot be silently overwritten.

## Owner checks before the team starts

- Confirm each employee login email and role in `Команда`.
- Confirm real customer prices and installer/material cost assumptions in `Услуги и цены`.
- Confirm monthly overhead, average deal and target-profit assumptions used for owner planning.
- Confirm installers can open their assigned workspace and `Рабочий день`.
- Confirm managers see only their scoped records and do not receive owner-only cost/overhead data.
- Send one controlled internal Proposal, open the public client link signed out, and verify the PDF before the first real customer send if this has not already been smoke-tested.

## Do not use tomorrow without separate verification

- Do not merge or rely on the old Stripe PR #31 as-is. Payment behavior must follow the current Agreement/Deposit rules and current configured payment methods.
- Do not guess film technical specifications or MP mappings. If a catalog mapping is not confirmed, enter verified characteristics manually.
- Do not treat the Money Tracker as bank reconciliation or formal accounting. It is the launch operational expense ledger.
- Do not delete legacy records or bulk-migrate customer/order data during the first working day.

## Known V1 limitations that do not block first-day operations

- Actual object expenses are an auditable PostgreSQL launch ledger, not yet the final normalized `accounts / money_movements / payables` finance schema.
- Quick estimates are currently saved as draft Proposal/KP snapshots rather than a dedicated versioned QuickEstimate entity.
- Full bank/cash reconciliation, tax-reserve accounting and company-wide P&L are later finance normalization work; they must not be inferred from the operational expense ledger.
- Warehouse normalization should be treated separately from first-day sales/project operation unless the live stock flow has been explicitly verified.

## First-day rule

For the first working day, prioritize clean data and one workflow over adding features: every lead in CRM, every estimate attached to a deal, every approved job launched only after Agreement + Deposit, every installer assigned through the system, and every project expense recorded the same day.

# Перенос действующих проектов: проверка перед переключением

Продолжение PR #296. Это план сверки, а не выполненная миграция.

## Проверка текущей базы без записи

На сервере с настроенным `DATABASE_URL`:

```sh
node --import tsx scripts/audit-legacy-project-migration.ts
```

Скрипт читает согласованный снимок (`REPEATABLE READ`) и устанавливает в PostgreSQL
`SET TRANSACTION READ ONLY`. Результат содержит номера записей, счётчики, кандидатов
для связи и причины остановки; имён клиентов, телефонов, публичных токенов и копии
исходного JSON в отчёте нет. Ревизия и SHA-256 снимка позволяют обнаружить изменения
после проверки. `ready_to_migrate` всегда false: проверка не заменяет сверку данных.

Скрипт не исправляет найденные проблемы и не запускается при deploy. Проверка рабочей базы выполнена 3 октября 2026 через существующее защищённое
окружение production в GitHub Actions (run 37114494044). Найдены четыре старых
заказа: три с замерами и один новый без замеров или строк услуг. У одного уже
есть сохранённое каноническое КП; проектных связей через эти КП не найдено.
Новый заказ без объёма нужно сохранить как черновик, а не удалять или заполнять
выдуманными данными. Полная сверка и фактическая миграция ещё не выполнены.

## Что связывается

| Источник | Целевые данные | Условие переноса |
| --- | --- | --- |
| `orders[].id` | Один `Project` | Нужна постоянная уникальная связь с исходным ID; сейчас отдельного ключа импорта в Project нет |
| `proposals[].orderId`, `canonicalProposalId`, `token` | `Proposal.project` | Использовать сохранённые ID или точное совпадение токена; не искать по названию, адресу или сумме |
| `orders[].clientId` | Один `Client` | Проверить контакты существующими правилами идентичности; конфликт телефона и email разрешается явно |
| `managerId`, `installerIds` | `User` | Только однозначные `legacy_user_ids`; совпадение имени не является доказательством |
| `measurements.rooms[].windows[]` | `ProjectPosition` и `Measurement` | Сохранить ID окна, комнату, единицы, плёнку, источники и ревизии; не объявлять предварительные размеры проверенными |
| Исторические `extraServices[quickProjectLine]` | `ProjectPosition` | Сохранить метраж, цену, даты и исполнителей каждой строки; не складывать повторно с замерами |
| `catalogId`, `manualFilmName` | `FilmCatalog` и историческая подпись | Нужна явная таблица соответствия; не создавать вымышленный остаток или нулевую закупочную стоимость |
| Даты услуги и её исполнители | `CalendarEvent` и `InstallerJob` | Проверить часовой пояс; несколько специалистов на одной услуге требуют отдельной доработки текущей уникальной связи позиции с заданием |
| Платежи, затраты, начисления, выплаты | Действующие финансовые записи и неизменяемые снимки | Сверить начислено и выплачено по сотруднику/услуге; импорт не должен повторно начислить зарплату или принять депозит |
| Timeline, документы, фото | История и `AttachmentFile` | Сохранить происхождение, порядок событий и ссылки; файлы не помещать в новые JSON-поля |

Предварительная связь через КП — только кандидат. Даже один найденный Project
нельзя считать полностью перенесённым: его услуги и финансовые записи могут
отличаться от текущего старого заказа. Несколько проектов-кандидатов или несколько
заказов на один Project блокируют автоматический перенос.

## Порядок переключения

1. Выполнить отчёт на актуальном снимке; разрешить все неоднозначные связи. Зафиксировать
   ревизию, постоянные ключи соответствия и источник каждого поля.
2. Реализовать применение как отдельную транзакцию с проверкой ревизии и уникальных
   ключей. Повторный запуск должен вернуть ранее созданные связи. Ошибка откатывает
   всю выбранную порцию. Отправка сообщений, списание сегодняшнего склада и запуск
   начислений при импортировании истории запрещены.
3. На копии базы сверить количество проектов и услуг, измеренные площади, суммы
   продаж/платежей/затрат, начисления и выплаты по сотрудникам, вложения и связи.
   Проверить повторный запуск, сбой посередине и конкурентное сохранение старой формы.
4. В той же границе переключения сделать старую запись только для чтения на сервере.
   Старый открытый браузер не должен перезаписать данные. Старые ссылки должны открывать
   единственный связанный Project; календарь и отчёты не должны считать его дважды.
5. После успешной репетиции выполнить проверенный перенос с резервной копией и отдельно
   проверить рабочую CRM. До этого PR #296 остаётся черновиком.

## Проверка пользователем после выпуска

Открыть услугу проекта → «Дата, исполнитель и заказ-наряд» → выбрать начало,
окончание и специалиста → «Назначить услугу». Открыть заказ-наряд и проверить адрес,
материал и исполнителя. Завершение услуги начисляет оплату один раз; незавершённые
услуги оставляют проект открытым. Это начисление, а не перевод денег сотруднику.

Еженедельная сводка и начисление менеджеру не реализованы этим PR. Для них требуется
отдельная сверка действующих правил оплаты после объединения проектных записей.
